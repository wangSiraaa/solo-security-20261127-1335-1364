# 离线器材互助库：保函签发与兑付（零依赖可运行模型）

回答题面那个核心问题：**四家寄存行都盖了足额章，并不自动等于两套借来的器材能在
同一天同时换回实物。** 足额章只对“某张收据对应的那件器材存在且在可用期内”负责；
能不能同时兑付，取决于独立托管席按 **同一履约日 + 互不相同的物理实体** 做的
**最不利同时兑付核定（worst-case simultaneous coverage）**。

本目录是题面第二路方案（独立托管席）的可运行实现，全部密码学为纯 Python、零第三方
依赖，并用 RFC 官方向量 + OpenSSL 交叉验证。

## 运行

```bash
python3 demo.py        # 端到端剧情（含反例、别名改判、兑付、离线柜台）
python3 test_suite.py  # 8 项确定性单元测试
```

## 文件

| 文件 | 职责 |
| --- | --- |
| `crypto.py` | Ed25519 签名(RFC 8032)、X25519(RFC 7748)、ChaCha20(RFC 8439)、HKDF、密封信封；导入即跑官方向量自检 |
| `model.py` | 规范化编码、合成物件 `SyntheticItem`、寄存行足额章 `BankReceipt`、成对器材订单 `PairedOrder` |
| `escrow.py` | 托管席：私有跨行物理台账、最不利同时兑付核定、密封保函、在线兑付、离线预留范围与 `OfflineCounter` |
| `client.py` | 客户视角：只开自己的密封保函，用独立配套图本地复核出库单，不信任全库 |
| `demo.py` | 题面完整剧情 |
| `test_suite.py` | 单元测试 |

## 关键不变量

1. **物理实体去重**：托管席私有 `physical_map: sid -> 物理实体标识`。多家为同一
   可拆套器材盖章会被折叠；公开数据只出现合成编号 `sid`，绝不出现物理名册/押物人。
2. **最不利同时兑付**：`worst_case_feasible` 在同一履约日，用回溯（二分图配对）为
   全部有效保函一次性分配互不相同的物理实体；任一单找不到合格镜身+转接环即整组 `under`。
3. **同日不可重复履约**：兑付时把物理实体记入 `spent_today[day]`，并公开一次性
   `nullifier` 防双花；零件可重组，但同一件实物不会出现在两套当日出库单里。
4. **别名攻击改判**：把某机构第二张收据改成同一实物的别名，会降低 distinct 实物数，
   覆盖组立即重判为 `under`（收据签名本身仍有效，失效的是“可同时覆盖”这一性质）；
   恢复收据后回到原组并就地覆盖为 `covered`。组 ID 只由“物理映射+订单集合”决定。
5. **客户最小可见面**：客户只收到密封给自己的保函（承诺、允许替代镜座、公差上限、
   兑付 nullifier）；公告板只有盲化标签、内容锚点、状态、nullifier、组根。
6. **离线柜台**：`OfflineCounter` 只持托管席公钥、签名 scope 副本和本地花费集，
   断网也能验签 + 用 scope 内公开描述符过配套图；超范围、篡改签名、双花一律拒办，
   回连后同步 nullifier。

## 剧情与题面要素对应

- 两家客户的**实际使用日签发时未知**：订单只写承诺窗口，`redeem(use_day, ...)`
  在使用日当天才确定，且按当日已交走部件重新匹配。
- **一种接受的替代镜座**：兑付入参 `chosen_alt_mount` 必须落在订单
  `allowed_mounts` 内；装配规则（镜座一致、镜身/环公差、环相对镜身+1µm）是
  托管席与客户端共用的同一份“配套图”，客户本地重算而非采信结论。
- **取件人独立装接与查回**：`ClientView.verify_manifest` 验托管席签名、各寄存行
  足额章、本地配套图、nullifier 一致性，并对篡改后的出库单判否。
- **先取走一只转接环后仍有效保函如何换件**：第二张保函在扣除当日已花费物理实体后
  重新跑可行性匹配，选出不同的环（demo 第 5、6 步），断言两单物理实体互不重叠。

## 与第一路（保留组）的关系

保留组（实物锁定到单张保函、清单交客户自验）提现快但限制库方后续调拨；本实现选择的
托管席路线靠最不利核定换取“能多接利用替代品的单”，代价是托管席必须实际维护多方
合同与私有跨行对应——该对应关系只存在于托管席私有内存，公告板与客户视图均不可推导。
